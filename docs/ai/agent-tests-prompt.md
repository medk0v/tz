# Промпт для отдельного чата: тестирование ИИ-агентов the workspace

В проекте `/Users/medk0v/Developer/other/tz` реализуй тестирование ИИ-агентов.

В настройках каждого сохранённого агента добавь отдельный блок «Тесты» под существующими блоками базы знаний и доступных каналов, в текущем стиле интерфейса.

Нужно:

1. Создание, редактирование, удаление и массовое добавление вопросов — каждый с новой строки. Поддержать многошаговые диалоги, язык, историю, состояние оператора и таймера.
2. Для сценария задаются ожидаемый смысл ответа, обязательные/запрещённые факты и действия, а также подготовленные результаты инструментов/API.
3. Запуск одного теста, выбранных тестов или всего набора на фактической модели агента с его сохранёнными инструкциями, публичным именем, разрешениями и назначенной опубликованной базой знаний.
4. Использовать общую с рабочим агентом сборку контекста и протокол инструментов. Не подменять проверку простым запросом к модели со всей базой знаний в промпте.
5. Два режима: повторяемый с подготовленными ответами API и отдельный режим разрешённых запросов к реальному API без изменения бизнес-данных. Подготовленный ответ выдавать только после правильного вызова инструмента с подходящими параметрами.
6. Изолировать побочные действия на уровне исполнения: тесты не должны писать клиентам, уведомлять реальных операторов, закрывать реальные чаты или создавать рабочие таймеры. Для таймера использовать виртуальное время и проверять отмену при подключении оператора/закрытии диалога. Проверку реального обработчика и доставки отделить от тестов ответов модели.
7. Показывать ответ агента, прочитанные статьи и версии, запросы и очищенные от секретов ответы API, последовательность действий, причины ошибок. Не показывать секреты и внутренние рассуждения модели.
8. Различать: пройдено, ошибка поведения, ошибка выполнения, нужна ручная оценка. Проверять факты и действия строгими условиями, смысл — отдельной оценкой. Одной оценки другой моделью недостаточно; критические сценарии проверять повторно.
9. Сохранять версии сценария, инструкции, базы знаний, модели и настроек инструментов. Помечать результаты устаревшими после изменений. Соблюдать существующие права tenant/project/inbox и не показывать чужие сценарии или результаты.
10. Формировать набор сценариев только по статьям назначенной опубликованной базы знаний. Темы, бизнес-правила, методы API и длительности таймеров конкретного клиента не должны быть зашиты в генератор сценариев. Дополнительные сценарии настраиваются по сохранённым инструкциям агента и его базе знаний.

Для API сверить реальные форматы результатов с кодом и доступной развёрнутой версией. Проверять null, отсутствующие поля, ошибки, противоречивые данные и попытки внедрения инструкций в текстовые поля. Учитывать, что обёртка инструмента может не передавать модели исходный HTTP-код. Не придумывать финансовые значения и ожидаемые результаты.

Правильность ожидаемых ответов сверяй с сохранёнными инструкциями выбранного агента, назначенной опубликованной базой знаний и подтверждёнными ответами API. Инструкции, статьи, контакты и правила конкретного клиента хранятся в базе на продакшене. Не сохраняй их копии, выгрузки, резервные копии или отчёты применения в репозитории проекта.

Реализуй функциональность, выполни необходимые проверки и отдельно укажи, что проверено локально, а что на работающем агенте. Не выдавай успешный тест текста за доказательство реальной доставки сообщения. Используй GPT-6 для работы над задачей; тестировать по умолчанию нужно фактическую модель выбранного агента.
